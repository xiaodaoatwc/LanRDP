# LanRDP macOS 性能优化计划（C / D / E）

范围：只做 C（AVC 直接 YUV）、D（渲染路径清理）、E（present 节流）。
A（自适应分辨率）、B（关闭渐进式编码）不在本次范围内。

## 预期收益

基于运行中会话的采样（视频播放、小窗口、CPU ~26%）：

| 环节 | 约占 CPU |
|---|---|
| 渐进式位图解码（DWT/RLGR/upgrade） | ~15% |
| 表面拷贝 | ~4% |
| YUV→RGB 转换 | ~2% |
| 纹理上传 / GPU | ~2% |
| H.264（VideoToolbox） | ≈0 |

- **D**：渲染目标全屏拷贝只影响 GPU/带宽，CPU 收益约 1~3%；
- **E**：当前内容约 30fps，present 已接近内容帧率，收益约 0~2%；
- **C**：视频区域的 YUV→RGB + RGB 上传可省掉，按视频占屏比例，约 3~8%（1080p 全屏视频可到 8~12%）。

**合计预期：CPU 相对下降 8%~15%**（视频占比越高越接近上限）。
若后续允许 B/A，可再降到 25%~50%，但不在本次范围。

## 实施步骤

### Step 0 测量（0.5~1 天）
- 在客户端加每阶段计时与编码类型统计（AVC420/444、progressive、raw），每秒写一条 `LanRDP perf:` 日志；
- 分别跑：静止桌面、滚动网页、视频（窗口/全屏）；
- 产出每阶段占比，用于确认 C 的收益上限和验收基线；
- 仪表只在测量包中启用，正式包默认关闭。

### Step 1 D：渲染路径清理（1 天）
- `blit` 的 dirty rect 上传保留；
- 当一帧的 damage 覆盖整个窗口时，直接渲染到窗口并 present，跳过 render target 的全屏拷贝；
- 部分 damage 时维持现有 render target 路径（保证背缓冲保留）；
- 验收：画面无闪烁/残影，CPU/GPU 略降。

### Step 2 E：present 节流（0.5 天）
- 记录上次 present 时间，距上次 < 8ms 的重复 present 合并；
- 无 damage 不 present；
- 验收：FPS 曲线不变、CPU 略降、输入延迟不变。

### Step 3 C：AVC420 直接 YUV（3~5 天）
- 在 gfx 解码路径中为 AVC420 提供可选的「YUV 帧 + 目标矩形」回调，跳过 RGB 转换；
- SDL 侧新增 IYUV 纹理层，和 RGB 底图合成；AVC444 继续走 RGB（SDL 无 444 纹理格式）；
- 位图更新与视频矩形重叠时，该帧回退 RGB 路径（保证正确性）；
- 验收：视频时 CPU 下降、上传带宽下降约 60%、无花屏/错位/残影。

### Step 4 验证与交付
- 每步独立构建测试包（b25、b26…），保留上一版可回退；
- 同一视频/窗口条件对比 CPU、FPS、带宽；
- 达标后合并、出正式包。

## 风险与回退

- C 涉及解码 → 渲染的数据通路，风险最高：保留 RGB 回退路径，任何异常自动走旧路径；
- D 影响呈现，若出现闪烁/残影，切回原路径（编译开关或回退提交）；
- E 若造成卡顿/输入延迟，调大阈值或关闭。

## 验收指标

- 1080p 全屏视频：CPU 下降 ≥ 6%（C+D+E 合计）；
- 窗口视频：CPU 下降 ≥ 3%；
- 带宽（视频）：下降 ≥ 30%；
- FPS 不降低、无新增花屏/撕裂/残影。
